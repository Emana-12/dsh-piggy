# Codex 小猪联动插件实现计划

> 日期：2026-10-12  
> 状态：按用户已确认的设计稿实施  
> 设计来源：[Codex 小猪联动插件设计](../specs/2026-10-12-codex-piggy-link-design.md)

## 目标与边界

交付一个可在本机 Codex 安装的完整插件：Codex 内能通过 MCP 工具养同一只桌面猪；Codex 钩子可将不含会话正文的工作事件记入成长。Electron 主进程仍是唯一存档所有者，插件永不自行打开或写入 state.json。保留上游规则、文案、素材与扩展行为。

本轮不发布插件目录、不发桌面安装包、不做云端同步；只有真实 Codex 与桌面程序验收通过后才报告端到端完成。若上游接口不足以安全完整覆盖既有子系统，应继续补齐，不以占位实现替代。

## 实施约束

- 在 `feat/codex-piggy-link` 独立分支开发；不覆盖用户现有文件，不提交或伪造提交身份。
- 只向 Electron 主进程请求现有 store API；新增本地 IPC 必须校验来源、绑定 ID、请求结构、超时与去重。
- Codex Hook 只映射白名单事件；不得读取/落盘/发送 transcript、prompt、代码、命令正文或工具参数；Hook 采用 Codex 支持的后台异步模式，错误不能阻断主任务。
- 新代码注释及新增用户文档用中文；遵守 `docs/CONVENTIONS.md` 的类型、模块职责与错误处理约束。
- 存档字段如需新增必须按 `core/upgrades.js` 迁移规约并保留旧数据。
- 不能用文件并发读写模拟跨端同步；状态必须由桌面进程内正在运行的 store 提供。

## 阶段一：协议与桌面桥只读通路

1. 固化 Codex 插件目录结构和安装方法：根 `plugin.json`、`.codex-plugin/plugin.json`（仅需兼容时）、MCP 配置、skills、hooks；根据官方最新文档选用可被本机 Codex 装载的格式。
2. 为桌面当前存档增加稳定的 `pigId`，确定不升级版本是否符合存档既有 ensure 模式；查清构造/迁移/导出路径。
3. 新建平台 IPC 模块：Windows 命名管道及 macOS/Linux Unix socket。主进程在唯一实例启动后创建、退出时关闭；权限只允许当前用户；Windows 路径使用用户 SID/稳定用户目录隔离。用有界长度的本地消息协议、协议版本、随机挑战/凭据或等效本地访问校验，避免同机其它进程无条件控制宠物。
4. 桌面主进程只暴露最小 RPC：配对信息、读取快照、状态变更订阅；每个连接先配对并携带 `pigId`。事件推送只发序列化快照或变更版本，不暴露任意路由/文件读写。
5. 编写独立 MCP stdio 服务：只连接 IPC；实现 `initialize`、工具发现、只读状态/配对查询、结构化结果及明确断连错误。MCP stdout 仅协议数据，日志写 stderr 且不含用户会话内容。
6. 验证 MCP stdio 生命周期、桌面启动/退出、重连、绑定 ID 不匹配；真实 Codex 未装载前不得宣称插件已被发现。

## 阶段二：受控养成工具与共享状态

1. 从 `routes.js`、`store/api.js`、`snapshot.js` 和四个 extension server 盘点真实可用操作及参数；建立显式工具/动作 allowlist，不执行任意路由名或函数名。
2. 将桌面 RPC 扩展为受控动作调用，所有写操作在 Electron 主进程顺序执行，并在边界内做类型、范围、枚举、确认值校验。
3. 设计高风险确认：重置/领养覆盖、删除扩展、影响资产或皮肤包的不可逆操作。MCP 输入必须包含显式用户确认标记；模型工具说明也必须要求先说明影响并取得用户确认。
4. 给每个写请求分配 requestId 并在桌面进程做有界时长去重缓存；超时后的状态查询返回已处理结果或不确定状态，严禁自动重复消费/结算。
5. 以现有快照返回所有玩法当前状态；覆盖照顾、日常、学习/工作/旅行、钓鱼、物品/商店/换装、图鉴、成就、日记、签到、番茄钟与菜园/矿洞/扭蛋/盲盒扩展。扩展输入仅交由各扩展公开 API 校验。
6. 验证 Codex 操作后桌面表现刷新、桌面面板操作后 Codex 查询即时更新、失败的业务结果和断连有清楚中文说明。

## 阶段三：Codex 工作事件映射

1. 对照当前 Codex 官方 Hook 事件和 JSON 输入格式，确定生命周期钩子与可获取的匿名事件字段；若事件格式含正文，仅抽取白名单字段，不记录原始输入。
2. 为 Codex 插件提供手动安装 hook 配置及脚本；钩子不隐式启用，安装说明明确信任确认和卸载步骤。
3. 事件通过本机 IPC 送到桌面 store 的现有 feed/适当核心 API；以 session 内稳定序号/事件 ID 去重，仅保留最小诊断数据与过期策略。
4. 钩子设置极短超时，桥离线时输出适合 Codex 的非阻断结果；验证可观测事件计数一次、错误/停止事件映射正确、工作区内容没有进入参数或日志。

## 阶段四：安装、生命周期与文档

1. 编写插件安装/启用/配对/重连/故障排查/卸载说明，分别覆盖 Codex Desktop 与 CLI 能力差异；明确桌面版必须启动及当前平台支持范围。
2. 若 Codex 支持本地插件目录/本地 marketplace，提供仓库内本地安装示例；不修改维护者个人配置、不自动全局安装。
3. 更新 `docs/ROADMAP.md` 的待办状态和 `CHANGELOG.md` 未发布段落，不改其它待决定玩法/台词/数值。
4. 检查新模块文件行数、类型、包产物、许可与打包清单；不将开发插件脚本意外带进游戏资源包。

## 阶段五：验证与交付

1. 先新增能失败的协议、身份绑定、参数白名单、幂等、断连和隐私回归测试；复用仓库测试方式，不改既有规则结果。
2. 运行相关测试、`npm test`、`npm run typecheck`；必要时构建桌面游戏包并检查 bundle 内容。
3. 在 Windows 真正启动桌面猪和 Codex，走配对、读状态、至少各一项 Codex/桌面写入、桥断开/重连、Codex hook 事件验收；检查两侧快照中的数值与 pigId 一致。
4. Linux/macOS socket 代码做平台级自动测试；若没有实际设备，明确标注未真实验收，不声称支持已验证。
5. 交付变更文件、测试结果、未完成的真实平台/宿主验收事项；不提交、不发布、不创建 PR，除非后续收到对应明确指令。

## 关键风险与处理

- Codex 官方插件打包格式会演进：实现前以 OpenAI 官方文档当前 schema 和本机 Codex 能力核对。
- IPC 不可当作认证边界：用当前用户权限、短期随机配对凭据和来源校验限制访问；协议绝不暴露通用 shell/文件 API。
- 桌面游戏包可热更新：桥调用动态游戏包 store API，RPC 版本协商并对缺失能力返回兼容错误。
- 两个 renderer 现有 snapshot 订阅可能只由 HTTP 请求触发刷新：桥写操作必须明确触发 `piggy:state-changed` 和猪表现通道，而不能只依赖 polling。
- 工作事件需避免重复奖励：事件 ID 在桌面进程侧唯一化、持久化或按核心规则确认幂等边界后再接入。
